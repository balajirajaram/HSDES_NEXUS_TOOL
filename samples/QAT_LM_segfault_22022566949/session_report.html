Root Cause / Final Hypothesis

During QEMU live migration of a QAT VF using vfio-pci with enable-migration=on and x-pre-copy-dirty-page-tracking=off, the VT-d interrupt remapping table entry (IRTE) for the QAT VF's MSI interrupt is not correctly restored on the destination. The MSI address field in the VT-d IRTE is left as 0x0 on the destination VM, causing QEMU's VT-d emulation to reject the first interrupt raised by the QAT hardware after migration completes. This propagates as a NULL MSI descriptor through the interrupt delivery path into cpa_sample_code's completion callback in libc.so.6, resulting in an instruction fetch from address 0x0 (error code 44) — a NULL function pointer call — and a fatal segmentation fault.

Evidence Chain

  • Iter 1 QAT qatlib 25.08/0.9.5 + BKC kernel 6.18.0 confirmed on DMR host
  • Iter 2 segfault at 0, error 44 in libc.so.6 at VM timestamp [98.8s] — NULL function pointer call via instruction fetch at address 0x0
  • Iter 2 vtd_interrupt_remap_msi: MSI address low 32 bit invalid: 0x0 — QEMU VT-d rejected interrupt due to null MSI address immediately before crash
  • Iter 2 TSC skew -11ms at same timestamp — confirms migration handoff just completed and state is unstable
  • Iter 3 IOMMU_IOAS_MAP failed: Bad address, PCI BAR? on source VF 0000:0f:00.1 — VF's BAR DMA mapping incomplete in VFIO container before migration
  • Iter 3 cpa_sample_code was actively running with high retry counts (up to 3.3M) on source — QAT VF had in-flight operations at migration trigger time
  • Iter 4 qat_vfio_pci 0000:0f:00.1 and 0001:0f:00.1 both bound and reset — correct driver in use but MSI-X table not persisted across migration boundary
  • Iter 4 x-pre-copy-dirty-page-tracking=off on both source and destination — dirty tracking disabled, device state sync relies entirely on atomic stop-and-copy

Recommended Fix

Primary fix (driver level): Ensure that qat_vfio_pci's migration save/restore operations include the MSI-X table entries. The VFIO PCI core's vfio_pci_msix_save / vfio_pci_msix_restore (or equivalent QAT-specific hooks) must be invoked as part of the VFIO migration save state sequence so that each MSI-X vector's address and data fields are serialized and restored on the destination.

Workaround (immediate): Try enabling dirty page tracking: replace x-pre-copy-dirty-page-tracking=off with x-pre-copy-dirty-page-tracking=on. This may not fully fix the issue but ensures device memory (including the MSI-X BAR page) is tracked and synced during pre-copy, reducing the window for a stale null IRTE.

Secondary fix (IOMMU): Investigate the IOMMU_IOAS_MAP failed: Bad address, PCI BAR? warnings. If the QAT VF's MSI-X BAR is not mapped in the iommufd IOAS, writes to the MSI-X table by the guest may not be visible to the VT-d interrupt remapping engine, leaving the IRTE stale.

Spec Reference: Intel VT-d Specification, §10.4 — Interrupt Remapping Table Entry (IRTE) format; MSI Address must be a valid LAPIC address (0xFEExxxxx range). Address = 0x0 is explicitly invalid and should not be written by QEMU during migration restore.
